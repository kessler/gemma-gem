# Gemma Gem Agent Bridge Design

## Recommendation

Expose Gemma Gem to other local/private agents through a local bridge, not by trying to make the Chrome extension itself speak directly to every agent runtime.

The best first target is a local MCP sidecar that the extension connects to over a localhost WebSocket. Add A2A as an optional peer-agent facade over the same local sidecar once the MCP tool surface is stable.

This keeps the browser extension private and Chrome-compliant while giving external agents a normal local protocol endpoint.

Do not add secondary transport fallbacks in code. The committed path is localhost WebSocket from the extension to the sidecar, and MCP from agent clients to the sidecar. Unsupported environments should fail clearly with setup instructions.

Chrome extensions cannot silently install or launch the sidecar. To avoid extra repository setup, distribute the sidecar as a package binary (`gemma-gem-bridge`) that MCP clients can launch directly, for example through `npx -y gemma-gem@latest`. Native Messaging can be added later as an optional installer-backed launch path, but it cannot be zero-setup because Chrome requires host registration outside the extension package. See `docs/platform-support.md` for the current cross-platform support notes.

## Why This Shape

Chrome extensions cannot simply open a general inbound server that other local processes can call. The better pattern is the one used by Playwright MCP's extension mode: a local MCP process runs on the machine, and the browser extension makes an outbound connection to that local process. Chrome Manifest V3 service workers support WebSockets, and Chrome 116+ can keep a service worker alive by exchanging WebSocket messages inside the 30 second activity window.

MCP is the right primary contract because Gemma Gem's current value to other agents is tool access:

- read page content
- click elements
- type into fields
- scroll
- capture screenshots
- execute page JavaScript
- ask Gemma Gem to complete a browser task

A2A is useful, but at a higher level: it describes Gemma Gem as a peer agent that can accept delegated browser tasks. It should wrap the same bridge and call the same internal extension commands rather than becoming the first protocol implemented.

## Proposed Architecture

```text
MCP client / local agent
        |
        | MCP stdio or Streamable HTTP
        v
gemma-gem-bridge
        |
        | localhost WebSocket relay
        v
Gemma Gem service worker
        |
        | existing runtime messages
        v
Offscreen Gemma agent <-> active tab content tools
```

Optional A2A facade:

```text
A2A client / peer agent
        |
        | HTTP JSON-RPC or SSE on 127.0.0.1
        v
gemma-gem-bridge
        |
        | same bridge commands
        v
Gemma Gem extension
```

## Bridge Components

### 1. Extension-side bridge client

Add an extension service worker bridge that connects to a local WebSocket endpoint, for example `ws://127.0.0.1:41587/extension`.

Responsibilities:

- keep a persistent authenticated WebSocket open when enabled
- send a keepalive message every 20 seconds while connected
- receive bridge requests from the local sidecar
- route requests to the existing service worker/offscreen/content-script message path
- stream agent chunks/tool events back to the local host
- enforce user-controlled enable/disable state

The right integration point is the background layer, near `background/message-router.ts`, because it already owns routing among the content script, offscreen model host, screenshot capture, and page JavaScript execution.

Background activity should also be surfaced to the content UI as **Gemma Relay** events. The MCP bridge remains the deterministic control path, but the page overlay should show a separate Relay view for delegated runs so a user can distinguish normal foreground chat from model-to-model browser work.

### 2. Local sidecar

Add a small Node/TypeScript package under `host/`.

Responsibilities:

- speak MCP over stdio for clients that launch local tools
- speak Streamable HTTP MCP in a separate explicit server mode when HTTP clients are targeted
- ship as a package binary so clients do not need this repository, `tsx` knowledge, or manual sidecar source paths
- expose a localhost WebSocket endpoint for the extension
- maintain request IDs and map local protocol calls to extension bridge messages
- enforce authentication with a local bearer token generated by the extension or install script
- bind only to localhost
- reject browser origins that are not explicitly allowed

This avoids Chrome native messaging installation complexity and keeps the bridge easy to run from normal local agent tools.

### 3. Shared bridge protocol

Add shared request/response types, separate from UI chat messages:

```ts
type BridgeRequest =
  | { type: 'bridge:list_tabs'; requestId: string }
  | { type: 'bridge:get_active_tab'; requestId: string }
  | { type: 'bridge:run_agent'; requestId: string; tabId?: number; prompt: string; settings?: ChatSettings }
  | { type: 'bridge:execute_tool'; requestId: string; tabId?: number; name: string; arguments: Record<string, unknown> }
  | { type: 'bridge:stop'; requestId: string; runId: string };

type BridgeEvent =
  | { type: 'bridge:response'; requestId: string; result?: unknown; error?: string }
  | { type: 'bridge:chunk'; requestId: string; text: string }
  | { type: 'bridge:tool_call'; requestId: string; name: string; arguments: Record<string, unknown> };
```

Keep this protocol lower level than MCP or A2A. MCP and A2A become adapters over it.

## MCP Surface

Model the high-level MCP surface after Stagehand's composable primitives:

- `gemma_tabs`: list visible tabs the extension can address
- `gemma_active_tab`: return active tab URL/title
- `gemma_observe`: discover relevant page actions or extraction targets from natural language
- `gemma_act`: perform one natural-language action or a previously observed action
- `gemma_extract`: return structured data from the active page, optionally constrained by selector and JSON schema
- `gemma_agent`: delegate a multi-step browser task to Gemma Gem
- `gemma_screenshot`: return visible screenshot
- `gemma_stop`: cancel an active delegated run

Keep lower-level tools private behind the bridge protocol:

- `read_page_content`
- `click_element`
- `type_text`
- `scroll_page`
- `run_javascript`
- `take_screenshot`

Expose `run_javascript` only through a separate development-only MCP tool if we deliberately decide to ship that capability. It should not be part of the default public tool set.

### Stagehand-Inspired Semantics

`gemma_observe` should return concrete candidate actions that can be executed later without another planning step:

```ts
type ObservedAction = {
  description: string
  method: 'click' | 'type' | 'scroll' | 'select' | 'navigate' | 'wait'
  arguments: unknown[]
  selector?: string
  ref?: string
  confidence?: number
}
```

`gemma_act` should be single-step. If a caller asks for multiple actions, return a clear validation error telling it to use `gemma_agent`.

`gemma_extract` should support structured schemas. The sidecar can accept JSON Schema from MCP clients and pass the schema intent to Gemma Gem, with the extension returning JSON that validates against the requested shape.

`gemma_agent` should run the existing offscreen Gemma agent loop for multi-step workflows.

Use existing tool definitions in `shared/tool-definitions.ts` for the low-level browser tools, but do not expose them without guardrails. `run_javascript` is powerful and should stay out of the default public MCP surface.

## A2A Surface

Add only after the MCP bridge works.

Expose a local Agent Card at:

```text
http://127.0.0.1:<port>/.well-known/agent-card.json
```

Suggested skill:

```json
{
  "id": "browser_task",
  "name": "Run browser task",
  "description": "Use a private Chrome extension agent to inspect and operate the active browser tab.",
  "tags": ["browser", "automation", "private", "local"],
  "inputModes": ["text/plain", "application/json"],
  "outputModes": ["text/plain", "application/json"]
}
```

The A2A `message/send` or streaming method should call the same internal `bridge:run_agent` operation used by `gemma_run_browser_task`.

## Security Model

Default posture should be local and explicit:

- disabled until the user enables "Local agent bridge"
- bind only to `127.0.0.1`
- require a bearer token or per-client generated secret
- show visible status in the extension when the bridge is connected
- show visible Relay activity when a local MCP client delegates browser work
- require confirmation before enabling any development-only JavaScript execution tool
- require per-origin or per-tab permission for high-impact actions
- log every external request in development builds
- never expose the local bridge on `0.0.0.0`
- never allow unauthenticated web pages to call the bridge

For local MCP HTTP, validate `Origin` headers and require auth. For the WebSocket relay, require a browser-profile token like Playwright MCP's extension bridge does. The token should be visible in Gemma Gem settings and accepted through an environment variable or sidecar config file.

## Implementation Plan

1. Add bridge types in `shared/bridge-messages.ts`.
2. Add a background WebSocket bridge client that dials `ws://127.0.0.1:<port>/extension`.
3. Add `host/` package with an MCP server and WebSocket relay.
4. Support MCP stdio first, then add `POST /mcp` using Streamable HTTP.
5. Implement MCP tools by translating calls into bridge messages.
6. Add extension settings for enabling the local bridge.
7. Add token setup and connection approval UI, following the Playwright MCP Bridge pattern.
8. Add optional A2A Agent Card and JSON-RPC methods over the same host.
9. Add tests for the WebSocket bridge, MCP tool schemas, and observe/act/extract behavior.

## Build Order

Build MCP first. It maps naturally to the extension's existing tool model and will let local agents use Gemma Gem as a browser tool provider quickly.

Then build A2A as a higher-level "Gemma Gem browser agent" endpoint for peer-to-peer task delegation.

Do not start with cross-extension messaging or externally connectable web pages. They are useful later for browser-to-browser integrations, but they do not solve the local private agent bridge as cleanly as a localhost MCP sidecar plus extension WebSocket bridge.

## Online Prior Art

- Playwright MCP supports extension mode with `npx @playwright/mcp@latest --extension`, connecting to existing Chrome or Edge tabs while reusing logged-in sessions, cookies, and installed extensions.
- The Playwright MCP Chrome Extension uses tab selection and a profile-specific `PLAYWRIGHT_MCP_EXTENSION_TOKEN` to bypass repeated connection approvals.
- Chrome documents WebSocket support in Manifest V3 extension service workers and recommends keepalive messages every 20 seconds on Chrome 116+.
- Chrome DevTools MCP is useful for debugging, tracing, console/network inspection, and performance audits. It is not a replacement for Gemma Gem's local model and page-task agent, but it is useful as a sibling MCP server.
- Browserbase/Stagehand's key design is the right product surface: `observe()` to plan, `act()` for one action, `extract()` for structured data, and `agent()` for multi-step autonomy. Gemma Gem should copy that abstraction while keeping execution local/private through the extension.
